# Kafka KRaft 모드: ZooKeeper 의존성을 제거한 이유와 발전 과정

Apache Kafka는 초기부터 클러스터 메타데이터 관리를 위해 **Apache ZooKeeper**에 의존해 왔습니다.  
하지만 2020년부터 시작된 **KRaft(Kafka Raft)** 프로젝트를 통해, Kafka는 ZooKeeper 없이도 동작할 수 있게 되었습니다.

이 글에서는 Kafka가 왜 ZooKeeper에서 KRaft로 전환하게 되었는지, 그 배경과 계기, 그리고 KRaft가 가져온 변화를 정리해보겠습니다.

---

## 1. Kafka와 ZooKeeper의 관계

### 초기 설계: ZooKeeper의 역할

Kafka가 처음 개발될 때(2011년), 클러스터 메타데이터 관리를 위해 ZooKeeper를 선택한 이유는 다음과 같습니다:

- **검증된 분산 코디네이션 도구**: ZooKeeper는 이미 널리 사용되던 분산 시스템 코디네이션 도구
- **빠른 개발**: 직접 구현하는 것보다 검증된 도구를 사용하는 것이 효율적
- **안정성**: 분산 합의 알고리즘(ZAB)을 통해 안정적인 메타데이터 관리 가능

**ZooKeeper가 담당했던 역할:**
- 브로커 등록 및 상태 관리
- 컨트롤러(Controller) 선출
- 토픽 메타데이터 저장
- 파티션 리더 선출 정보 저장
- ACL(Access Control List) 정보 저장

### 아키텍처의 복잡성

```
┌─────────────┐
│   Producer  │
└──────┬──────┘
       │
       ▼
┌─────────────┐     ┌─────────────┐
│   Broker    │◄────┤  ZooKeeper  │
│   Cluster   │     │   Cluster   │
└──────┬──────┘     └─────────────┘
       │
       ▼
┌─────────────┐
│   Consumer  │
└─────────────┘
```

이러한 아키텍처는 **두 개의 분산 시스템을 운영**해야 한다는 복잡성을 야기했습니다.

## 2. ZooKeeper 의존성의 문제점

### 운영 복잡성 증가

**1. 두 개의 클러스터 운영**
- Kafka 클러스터와 ZooKeeper 클러스터를 별도로 운영해야 함
- 각각의 모니터링, 백업, 장애 대응 필요
- 운영 인력과 리소스가 두 배로 필요

**2. 버전 호환성 문제**
- Kafka 버전과 ZooKeeper 버전 간 호환성 관리 필요
- Kafka 업그레이드 시 ZooKeeper 버전도 함께 고려해야 함
- 의존성 업그레이드가 복잡함

**3. 설정 및 튜닝 복잡도**
- Kafka 설정과 ZooKeeper 설정을 모두 이해해야 함
- 두 시스템의 튜닝이 서로 영향을 미칠 수 있음

### 확장성 제약

**1. 메타데이터 크기 제한**
- ZooKeeper는 **전체 메타데이터를 메모리에 저장**
- 토픽과 파티션이 많아질수록 메타데이터 크기 증가
- **수백만 개의 파티션**을 지원하기 어려움

**2. 컨트롤러 선출 속도**
- ZooKeeper를 통한 컨트롤러 선출은 상대적으로 느림
- 장애 복구 시간이 길어짐

**3. 트랜잭션 처리 성능**
- 메타데이터 변경 시 ZooKeeper와의 통신 오버헤드
- 대규모 클러스터에서 성능 병목 발생

### 장애 복구 속도

**1. 컨트롤러 장애 시**
- ZooKeeper를 통한 새로운 컨트롤러 선출 과정이 필요
- 선출 과정에서 일시적인 서비스 중단 가능

**2. 메타데이터 동기화**
- ZooKeeper와 Kafka 브로커 간 메타데이터 동기화 지연
- 변경 사항이 모든 브로커에 전파되는 데 시간 소요

---

## 3. KRaft 모드의 등장 배경

### Raft 알고리즘의 선택

Kafka 커뮤니티는 ZooKeeper를 대체하기 위해 **Raft 합의 알고리즘**을 선택했습니다.

**Raft 알고리즘의 특징:**
- **이해하기 쉬움**: 분산 합의 알고리즘 중 비교적 이해하기 쉬운 구조
- **안정성**: Leader 선출과 로그 복제를 통해 일관성 보장
- **성능**: ZooKeeper의 ZAB보다 더 효율적인 구현 가능

### KRaft 프로젝트의 시작

**KIP-500 (Kafka Improvement Proposal 500)**
- 2019년 제안된 KIP-500은 ZooKeeper 제거를 목표로 함
- Kafka 자체 내에서 메타데이터를 관리하는 메커니즘 도입
- Raft 알고리즘을 기반으로 한 컨트롤러 그룹(Controller Quorum) 구성

**개발 타임라인:**
- 2020년: KRaft 프로젝트 시작
- 2021년: Kafka 2.8.0에서 KRaft 모드 Early Access
- 2022년: Kafka 3.3.0에서 KRaft 모드 Production Ready
- 2023년: Kafka 3.5.0에서 KRaft가 기본 모드로 전환
- 2024년 말/2025년 초: **Kafka 4.0.0 출시, ZooKeeper 지원 완전 제거 완료**

---

## 4. KRaft 모드의 아키텍처

### 컨트롤러 그룹(Controller Quorum)

KRaft 모드에서는 **컨트롤러 그룹**이 메타데이터를 관리합니다.

```
┌─────────────┐
│   Producer  │
└──────┬──────┘
       │
       ▼
┌─────────────────────────────────┐
│      Broker Cluster             │
│  ┌──────────┐  ┌──────────┐     │
│  │ Broker 1 │  │ Broker 2 │     │
│  │(Controller)│ │(Controller)│  │
│  └──────────┘  └──────────┘     │
│  ┌──────────┐                   │
│  │ Broker 3 │                   │
│  │(Controller)│                 │
│  └──────────┘                   │
└─────────────────────────────────┘
       │
       ▼
┌─────────────┐
│   Consumer  │
└─────────────┘
```

**주요 변화:**
- ZooKeeper 클러스터 제거
- Kafka 브로커 중 일부가 컨트롤러 역할 수행
- 컨트롤러 그룹 내에서 Raft 알고리즘으로 합의

### 메타데이터 저장 방식

**ZooKeeper 모드:**
- 메타데이터가 ZooKeeper에 저장
- 브로커는 ZooKeeper에서 메타데이터를 읽어옴
- 메모리 기반 저장으로 크기 제한

**KRaft 모드:**
- 메타데이터가 **컨트롤러의 로그 파일**에 저장
- 디스크 기반 저장으로 **수백만 개의 파티션** 지원 가능
- 브로커는 컨트롤러로부터 메타데이터를 받아 캐시

---

## 5. KRaft 모드의 주요 개선사항

### 1. 운영 간소화

**단일 클러스터 운영**
- Kafka 클러스터만 운영하면 됨
- ZooKeeper 클러스터 운영 불필요
- 모니터링, 백업, 장애 대응이 단순해짐

**버전 관리 단순화**
- Kafka 버전만 관리하면 됨
- 의존성 업그레이드가 간단해짐

### 2. 성능 향상

**메타데이터 처리 속도**
- ZooKeeper 통신 오버헤드 제거
- 컨트롤러와 브로커 간 직접 통신으로 **트랜잭션 속도 향상**

**장애 복구 속도**
- 컨트롤러 선출이 더 빠름
- 리더 선출 및 장애 복구 시간 단축

### 3. 확장성 증가

**대규모 파티션 지원**
- 디스크 기반 메타데이터 저장으로 **수백만 개의 파티션** 지원 가능
- 메모리 제약에서 벗어남

**클러스터 확장성**
- 더 많은 브로커와 토픽을 효율적으로 관리 가능

### 4. 안정성 향상

**단일 시스템 운영**
- 두 시스템 간 동기화 문제 제거
- 장애 지점 감소

**일관성 보장**
- Raft 알고리즘을 통한 강력한 일관성 보장
- 메타데이터 변경의 원자성 보장

---

## 6. KRaft 모드의 동작 원리

### 컨트롤러 선출

**Raft 알고리즘 기반:**
1. 컨트롤러 그룹 내에서 **Leader 선출**
2. Leader가 메타데이터 변경을 처리
3. Follower는 Leader의 변경 사항을 복제

**장애 시:**
- Leader 장애 시 새로운 Leader 선출
- 선출 과정이 ZooKeeper보다 빠름

### 메타데이터 전파

**1. 메타데이터 변경 요청**
- 브로커나 관리자가 메타데이터 변경 요청
- 예: 토픽 생성, 파티션 추가 등

**2. 컨트롤러 Leader 처리**
- Leader가 변경 사항을 로그에 기록
- Follower들에게 복제

**3. 브로커에 전파**
- 변경된 메타데이터를 브로커들에게 전파
- 브로커는 메타데이터를 캐시

### 로그 기반 메타데이터

**KRaft 메타데이터 로그:**
- 모든 메타데이터 변경이 로그에 기록됨
- 디스크에 저장되어 영구 보존
- 장애 복구 시 로그를 재생하여 상태 복원

## 7. 마이그레이션 전략

### 점진적 전환

**1. KRaft 모드 테스트**
- 개발/테스트 환경에서 KRaft 모드 테스트
- 운영 환경과 유사한 조건에서 검증

**2. 단계적 마이그레이션**
- Kafka 3.x에서는 ZooKeeper 모드와 KRaft 모드 공존 가능
- **Kafka 4.0.0 이상에서는 KRaft 모드만 지원**하므로, 3.x에서 4.x로 업그레이드 전에 반드시 KRaft 모드로 전환해야 함
- 점진적으로 KRaft 모드로 전환하는 것이 권장됨

**3. 완전 전환**
- 모든 클러스터를 KRaft 모드로 전환
- ZooKeeper 클러스터 제거

### 주의사항

**1. 버전 호환성**
- Kafka 3.3.0 이상에서 KRaft 모드 Production Ready
- **Kafka 4.0.0부터는 ZooKeeper 지원이 완전히 제거됨 (2025년 현재 적용됨)**
- 신규 클러스터는 반드시 KRaft 모드로 시작해야 함

**2. 메타데이터 백업**
- 마이그레이션 전 메타데이터 백업 필수
- 롤백 계획 수립

**3. 모니터링 강화**
- KRaft 모드 전환 후 모니터링 강화
- 컨트롤러 그룹 상태 지속적 관찰

## 8. KRaft 모드의 현재 상태와 미래

### 현재 상태 (2025년 12월 기준)

**Kafka 4.0.0 출시 완료:**
- **2024년 말/2025년 초에 Kafka 4.0.0이 정식 출시됨**
- **ZooKeeper 지원이 완전히 제거**되었고, KRaft 모드가 유일한 옵션이 되었습니다
- 새로운 Kafka 클러스터는 반드시 KRaft 모드로 시작해야 함
- ZooKeeper 모드로는 더 이상 클러스터를 생성할 수 없음

**기업들의 마이그레이션 현황:**
- 많은 기업들이 Kafka 3.x에서 4.0.0으로 업그레이드하며 KRaft 모드로 전환 완료
- 주요 클라우드 서비스(AWS MSK, Confluent Cloud, Azure Event Hubs 등)에서 KRaft 모드를 기본 모드로 지원
- 기존 ZooKeeper 모드 클러스터는 여전히 운영 가능하지만, 신규 클러스터는 KRaft만 가능

**KRaft 모드의 안정성:**
- Production 환경에서 충분히 검증됨
- 대규모 클러스터(수백만 개의 파티션)에서도 안정적으로 동작
- 컨트롤러 장애 복구 시간이 ZooKeeper 모드 대비 크게 단축됨

**성능 개선 실적:**
- 메타데이터 처리 속도가 ZooKeeper 모드 대비 **약 2~3배 향상**
- 토픽 생성, 파티션 추가 등의 작업이 더 빠르게 처리됨
- 컨트롤러 선출 시간이 **수백 밀리초에서 수십 밀리초로 단축**

**클라이언트 애플리케이션 호환성:**
- **Spring Boot 4.0.0과 KRaft 모드의 Kafka 4.0.0은 완전히 호환됨**
- KRaft는 서버 측 메타데이터 관리 방식의 변경이므로, 클라이언트 애플리케이션에는 큰 영향이 없음
- `spring-kafka` 라이브러리는 Kafka 클라이언트 API를 래핑하므로, 서버가 ZooKeeper 모드든 KRaft 모드든 동일하게 동작
- Spring Boot 4.0.0에 포함된 `spring-kafka` 버전이 Kafka 4.0.0 클라이언트를 지원하므로 별도 설정 없이 사용 가능
- 기존 Spring Boot 애플리케이션 코드 변경 없이 KRaft 모드 Kafka 클러스터에 연결 가능

### 미래 전망

**Kafka 4.x 버전의 발전:**
- KRaft 모드를 기반으로 한 새로운 기능들이 지속적으로 추가되고 있음
- 메타데이터 관리의 효율성 향상
- 더 나은 확장성과 성능 개선

**기능 확장:**
- **Self-Balancing**: KRaft 모드에서 파티션 리밸런싱이 더 효율적으로 동작
- **Incremental Metadata Updates**: 메타데이터 변경 시 전체 동기화가 아닌 증분 업데이트
- **Improved Security**: KRaft 모드에서의 보안 기능 강화

**ZooKeeper 모드의 종료:**
- Kafka 3.x 버전은 여전히 유지보수되지만, 새로운 기능은 KRaft 모드에 집중
- 기존 ZooKeeper 모드 클러스터는 점진적으로 KRaft 모드로 마이그레이션 권장
- 향후 Kafka 5.0.0에서는 ZooKeeper 관련 코드가 완전히 제거될 예정

## 9. 정리 및 마무리

이 글에서는 Kafka가 ZooKeeper에서 KRaft 모드로 전환하게 된 배경과 계기, 그리고 KRaft가 가져온 변화를 정리해보았습니다.

**핵심 포인트:**

- **ZooKeeper 의존성의 문제점**
  - 운영 복잡성 증가 (두 개의 클러스터 운영)
  - 확장성 제약 (메타데이터 크기 제한)
  - 장애 복구 속도 느림

- **KRaft 모드의 등장**
  - Raft 알고리즘 기반의 컨트롤러 그룹
  - Kafka 자체 내에서 메타데이터 관리
  - ZooKeeper 클러스터 제거

- **KRaft 모드의 개선사항**
  - 운영 간소화 (단일 클러스터)
  - 성능 향상 (트랜잭션 속도, 장애 복구)
  - 확장성 증가 (수백만 개의 파티션 지원)
  - 안정성 향상 (단일 시스템 운영)

**2025년 12월 시점의 현황:**

- **Kafka 4.0.0이 정식 출시**되어 ZooKeeper 지원이 완전히 제거됨
- 신규 Kafka 클러스터는 반드시 KRaft 모드로 시작해야 함
- 많은 기업들이 KRaft 모드로 전환을 완료했고, Production 환경에서 안정적으로 운영 중
- 성능 개선 실적이 확인됨 (메타데이터 처리 속도 2~3배 향상, 컨트롤러 선출 시간 대폭 단축)
- 주요 클라우드 서비스에서 KRaft 모드를 기본으로 지원

Kafka의 이러한 발전은 **분산 시스템의 진화**를 보여주는 좋은 사례입니다. 외부 의존성을 줄이고 자체적으로 핵심 기능을 구현함으로써, 더 단순하고 효율적인 아키텍처를 달성할 수 있었습니다. 2025년 현재, KRaft 모드는 Kafka의 표준이 되었고, 앞으로도 지속적인 개선이 예상됩니다. 🚀
