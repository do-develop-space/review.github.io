이전 글에서 **멱등성 키 기반 동시성 제어**를 통해 DB 레벨에서 중복 처리를 방지하는 방법을 다뤘습니다. 이번 글에서는 **Kafka 메시징 시스템에서 메시지의 안정성과 내구성을 보장하는 acks 옵션**에 대해 정리해보겠습니다.

## Kafka acks 옵션이란?

Kafka 프로듀서는 `acks` 옵션으로 **메시지를 전송한 뒤 얼마만큼의 확인(acknowledgement)을 기다릴지**를 설정할 수 있습니다.
이 값에 따라 **지연 시간, 처리량, 데이터 유실 가능성**이 크게 달라집니다.

- **acks=0**: 전송만 하고 응답을 기다리지 않음 (fire-and-forget)
- **acks=1**: **리더 파티션**이 쓰기를 확인하면 OK
- **acks=all (또는 -1)**: 리더 + **ISR(동기화된 팔로워들)**까지 쓰기를 확인해야 OK

이 글에서는 **acks=1**과 **acks=all**을 중심으로, **언제 어떤 걸 선택해야 하는지**, **안정성(내구성) 차이가 얼마나 큰지**를 정리해 보겠습니다.

> 참고: 2025-12-31 글에서 **Kafka 재시도와 멱등성(idempotence)**를 다뤘다면, 이번 글은 그보다 한 단계 아래 레벨인 **브로커 쓰기 정책(acks)** 자체에 초점을 맞춥니다. 또한 1월 10일 글에서 다룬 **DB 레벨의 멱등성과 동시성 제어**와 마찬가지로, 메시징 시스템에서도 메시지의 안정성과 중복 방지가 중요합니다.

## 0. 브로커 / 파티션 / 리더 / ISR 한 번에 정리

acks 이야기를 이해하려면, 먼저 **Kafka가 데이터를 어떻게 나누고 복제하는지**를 같이 보는 게 좋습니다.

### 0.1 브로커(Broker)

- **Kafka 서버 프로세스 1개 = 브로커 1개**라고 보면 됩니다.
- 실제로 메시지를 디스크에 저장하고, 프로듀서/컨슈머와 통신하는 주체입니다.
- 보통 3개 이상 브로커를 띄워서 클러스터를 구성합니다.

```text
브로커 3대 예시

Broker-1 (kafka-broker-1)
Broker-2 (kafka-broker-2)
Broker-3 (kafka-broker-3)
```

### 0.2 파티션(Partition)

- **토픽을 쪼개 놓은 조각**입니다.
- 예를 들어 `reservation-events` 토픽을 3 파티션으로 만들면:

```text
reservation-events-0
reservation-events-1
reservation-events-2
```

- 각 파티션은 **append-only 로그 파일**이고, 메시지는 키(예: reservationId)에 따라 특정 파티션으로 라우팅됩니다.
- 중요한 포인트:
  - **순서 보장은 파티션 단위**로만 됩니다.
  - 파티션 수를 늘리면 **부하 분산/처리량은 늘지만, 순서 보장 범위는 쪼개짐**.

### 0.3 리더(Leader)와 팔로워(Follower)

- 각 파티션은 항상 **리더 브로커 1개**와 **팔로워 브로커 여러 개**로 구성됩니다.

```text
reservation-events-0 파티션 예시

Leader  : Broker-1
Follower: Broker-2
Follower: Broker-3
```

- **프로듀서/컨슈머는 항상 리더에게만 읽고/쓴다**고 이해하면 됩니다.
  - 프로듀서 → 리더 파티션에 쓰기
  - 컨슈머 → 리더 파티션에서 읽기
- 팔로워는 리더의 로그를 계속 따라가며 데이터를 복제합니다.
  - 나중에 리더가 죽으면, 팔로워 중 하나가 **새 리더로 승격**됩니다.

### 0.4 ISR (In-Sync Replica)

- **리더와 “충분히 동기화된” 레플리카의 집합**입니다.
- 항상 **리더 1개 + 잘 따라가고 있는 팔로워들**로 구성됩니다.

```text
ISR 예시

Partition: reservation-events-0
Leader  : Broker-1
ISR     : { Broker-1, Broker-2 }   # Broker-3은 느려서 ISR에서 제외되었다고 가정
```

- acks=all에서 중요한 건:
  - **“리더 + ISR에 포함된 모든 레플리카에 쓰기가 반영되었는가?”** 입니다.
  - ISR에 포함되지 않은 느린 팔로워는 acks=all 보장 범위에서 제외됩니다.

> 이 구조를 머릿속에 두고 보면, 뒤에서 나올  
> **“acks=1은 리더만 믿는 것, acks=all은 리더 + ISR까지 확인하는 것”** 이라는 문장이 훨씬 직관적으로 들어옵니다.

## 1. acks 옵션별 동작 정리

### 1.1 acks=0

- **동작**
  - 프로듀서가 브로커로 **메시지를 전송만 하고**, **아무 응답도 기다리지 않음**
  - 브로커에 도달했는지, 파티션에 잘 써졌는지 확인하지 않음
- **특징**
  - **가장 빠름** (네트워크 송신만 하면 바로 다음 메시지로 진행)
  - 하지만 **브로커 다운, 네트워크 오류, 쓰기 실패**를 전혀 감지하지 못함
  - **데이터 유실 가능성이 가장 큼**
- **언제?**
  - 로그/메트릭처럼 **약간의 유실을 허용할 수 있는 경우**
  - 또는, **어차피 다른 경로로도 데이터가 남는 보조 데이터 스트림**일 때

### 1.2 acks=1

- **동작**
  - 메시지가 **리더 파티션**에 쓰인 직후, 리더가 프로듀서에게 **성공 응답**을 보냄
  - 팔로워 복제(replication)는 **비동기**로 나중에 따라옴
- **특징**
  - **지연 시간과 처리량이 좋음**
  - **리더 브로커에 쓰기만 성공하면 OK**라서 빠름
  - 하지만 **리더가 쓰기 직후 죽고, 팔로워가 아직 복제하지 못했다면 데이터 유실 가능**
- **언제?**
  - **내구성이 중요하지만, 극단적인 상황에서 일부 유실은 감수할 수 있는 서비스**
  - 트래픽이 많고, **Latency/Throughput이 중요**한 경우 일반적인 기본값

### 1.3 acks=all (또는 -1)

- **동작**
  - 메시지가 **리더 + ISR에 포함된 모든 팔로워**에 쓰인 뒤에야 프로듀서에게 OK 응답
  - 복제 팩터(replication.factor)와 `min.insync.replicas` 설정에 영향을 받음
- **특징**
  - **가장 안전(내구성 최고)**: 리더가 죽어도 팔로워에 복제된 데이터가 남음
  - 대신 **지연 시간 증가** 가능성, **처리량 감소** 가능성
  - ISR에 있는 팔로워가 느리면 전체 쓰기가 느려질 수 있음
- **언제?**
  - **금융 결제, 주문, 예약 등 절대 유실되면 안 되는 데이터**
  - 멱등성 + 재시도와 조합해 **거의-한번-만 전달(Exactly-once에 가까운)** 보장을 추구할 때

## 2. acks=1 vs acks=all: 어떤 차이가 있나?

### 2.1 정상적인 상황에서의 차이

**전제 조건**

- replication.factor=3 (리더 1개 + 팔로워 2개)
- 브로커/네트워크 상태가 양호

이때를 가정하면:

- **acks=1**
  - 리더 쓰기 성공 후 바로 응답
  - 팔로워 복제는 백그라운드에서 이어짐
  - **지연 시간: 짧음**
  - **처리량: 높음**
- **acks=all**
  - 리더 + ISR 팔로워 2곳까지 쓰기가 끝나야 응답
  - 팔로워가 빠르면 **체감상 acks=1과 큰 차이 없을 수도 있음**
  - 하지만 일반적으로 **조금 더 느리고, 처리량은 더 낮을 수 있음**

**정상적인 상황**에서는 사실 **둘 다 문제가 거의 없고**, 차이는 주로 **Latency/Throughput 관점**입니다.

### 2.2 장애 상황에서의 차이 (핵심)

진짜 차이는 **장애 시나리오**에서 드러납니다.

#### 케이스 1: 리더에만 쓰고, 팔로워 복제 전에 리더 브로커 죽음

- **공통 설정**
  - replication.factor=3
  - ISR = {리더, 팔로워1, 팔로워2}

**1) acks=1인 경우**

1. 프로듀서 → 리더에 쓰기
2. 리더가 Local Log에 기록하고 바로 **OK 응답 전송**
3. 프로듀서 입장: \"성공\"으로 처리
4. 아직 팔로워는 복제 전
5. 이때 리더 브로커가 장애로 다운
6. 새로운 리더 선출:
   - **팔로워들 중 최근까지 복제된 노드**가 리더가 됨
7. 하지만 **문제의 메시지는 팔로워에 복제되지 않았으므로 유실**

- 결과:
  - 프로듀서는 성공했다고 믿지만
  - 브로커 측에서는 **해당 메시지가 사라짐 → 데이터 유실**

**2) acks=all인 경우**

1. 프로듀서 → 리더에 쓰기
2. 리더가 Local Log에 기록
3. 동시에 ISR 팔로워 2곳으로 복제 요청
4. 팔로워 2곳 모두 쓰기 성공 후에야 **OK 응답 전송**
5. 그 이후 리더 브로커가 다운된다면?
   - 팔로워 중 하나가 새 리더가 됨
   - **문제의 메시지가 팔로워에도 있으므로 유지**

- 결과:
  - 프로듀서가 성공 응답을 받은 메시지는
  - **최소 2개의 브로커(리더 + 팔로워)에 존재**
  - 리더 장애에도 **데이터 유실 없이 복구 가능**

> **정리:**  
> - acks=1: 리더에만 쓰고 리더가 죽으면 **유실 가능**  
> - acks=all: ISR에 복제된 뒤 응답하므로 **리더 장애에도 유실 방지**

#### 케이스 2: ISR 축소 & min.insync.replicas

**acks=all이 항상 완벽한 건 아닙니다.** 중요한 설정이 하나 더 있습니다: `min.insync.replicas`.

- 예: `replication.factor=3`, `min.insync.replicas=2`
  - ISR에 **최소 2개 브로커**가 있어야 `acks=all` 쓰기가 성공
  - ISR이 1개로 줄어들면 쓰기 요청을 **실패로 응답** (데이터 유실을 막기 위해)

반대로:

- `min.insync.replicas=1`로 설정하면?
  - ISR이 1개(리더만) 남아도 `acks=all`을 만족하는 것으로 간주
  - 이때 사실상 **acks=1과 내구성 수준이 비슷해짐**

> **따라서, 진짜 안정성을 위해서는**
> - `acks=all` **+** `replication.factor >= 3` **+** `min.insync.replicas >= 2`  
> - 이 조합이 함께 맞춰져야 합니다.

## 3. 안정성(내구성)은 어디가 더 좋은가?

### 3.1 내구성 관점 비교

- **acks=1**
  - 리더에만 쓰기 성공해도 OK
  - 리더 장애 시, 팔로워가 해당 메시지를 못 받았으면 **유실 가능**
  - replication.factor를 크게 잡아도, **쓰기 시점에 팔로워가 못 받으면 소용 없음**

- **acks=all**
  - ISR에 포함된 팔로워까지 **실제 쓰기가 보장된 후** OK
  - 리더 장애 시에도, 팔로워에 데이터가 남아 있을 가능성이 높음
  - 특히 `min.insync.replicas >= 2`라면, **최소 2개 브로커에 복제된 후에만 성공 처리**

**결론 (내구성/안정성):**

- **acks=all이 acks=1보다 훨씬 안전**합니다.
- 단, **설정이 제대로 되어 있을 때**:
  - `replication.factor >= 3`
  - `min.insync.replicas >= 2`

### 3.2 가용성/성능까지 함께 보는 경우

하지만 현실 시스템에서는 **내구성만** 볼 수 없습니다.  
**가용성(에러 없이 쓰기가 계속 들어가는 것)**과 **성능(지연 시간, 처리량)**도 함께 고려해야 합니다.

- **acks=1**
  - **가용성:** 높음
    - 팔로워가 조금 느려도 리더만 살아 있으면 계속 쓰기 가능
  - **성능:** 좋음
    - 지연 시간 짧고 처리량 높음
  - **내구성:** 중간
    - 리더 장애 시, 방금 쓴 메시지가 유실될 수 있음

- **acks=all**
  - **가용성:** 상대적으로 낮을 수 있음
    - ISR이 줄어들면 쓰기가 실패할 수 있음 (`min.insync.replicas` 조건)
  - **성능:** 일반적으로 acks=1보다 느림
    - ISR 팔로워까지 쓰기를 기다려야 함
  - **내구성:** 높음
    - 장애 상황에서도 데이터가 남을 확률이 매우 높음

> **트레이드오프 요약**
> - acks=1: **성능/가용성** 우선, 약간의 유실 허용  
> - acks=all: **내구성** 우선, 성능/가용성 희생 가능

## 4. acks 설정 시 함께 고려해야 할 것들

### 4.1 replication.factor

- 최소 **3 이상**을 권장
- replication.factor=1이면:
  - acks=1이나 all이나 **차이가 거의 없음** (팔로워가 없으므로)
  - 브로커 하나 죽으면 그대로 데이터 유실

### 4.2 min.insync.replicas

- 예시:

```properties
replication.factor=3
min.insync.replicas=2
```

- 이 때:
  - **acks=all**이면, ISR에 최소 2개 브로커가 있어야 쓰기 성공
  - ISR이 1개로 줄어들면, 쓰기 요청이 실패 (에러 반환)
  - 이 에러는 프로듀서가 **재시도 정책으로 처리**하게 됨

### 4.3 프로듀서 재시도 & 멱등성

- **acks=all + `enable.idempotence=true` + 재시도** 조합은
  - 중복 쓰기를 방지하면서
  - \"성공 응답을 받은 메시지는 거의 절대적으로 유실되지 않는다\"에 가까운 수준
- 단, 이 경우에도:
  - **완전한 의미의 Exactly-once**는 아니고
  - \"**중복 없는 At-least-once**에 아주 가까운 수준\"으로 이해하는 것이 현실적

## 5. 어떤 서비스에서 무엇을 쓸까?

### 5.1 acks=1을 써도 되는 경우

- **로그/메트릭/트래킹 이벤트**
  - GA 이벤트처럼, 일부 유실은 통계적으로 보완 가능
  - 사용자 경험에 직접적인 영향을 주지 않음
- **캐시 갱신 이벤트**
  - 어차피 원본 DB가 진실(Source of Truth)
  - 이벤트 몇 개 날아가면, 다음 갱신 때 다시 맞춰짐
- **성능이 최우선인 실시간 처리**
  - 극단적인 저지연이 필요한 경우 (예: 게임 실시간 매칭 로그 등)

### 5.2 acks=all이 강하게 권장되는 경우

- **주문/결제/예약/포인트 적립/쿠폰 발급**
  - 한 번의 유실이 **바로 금전적 손해/도메인 불일치**로 이어지는 경우
  - 이후 보정(batch)으로도 추적이 어렵거나, 고객 신뢰에 치명적인 경우
- **재고 감소/좌석 차감/한정 수량 이벤트**
  - 메시지가 유실되면 재고/좌석 상태가 실제와 달라짐
  - 이후에 복구하려면 매우 복잡한 보정 로직 필요

> **요약:** 돈, 재고, 예약, 한정 자원과 직결되는 이벤트는 **acks=all**을 기본으로 생각하는 것이 좋습니다.

---

## 6. 정리: \"안정성은 어디가 더 좋은가?\"

- \"안정성\"을 **데이터 내구성(유실 가능성)** 기준으로 보자면:
  - **acks=all**이 **명확하게 더 좋습니다.**
  - 단, `replication.factor`와 `min.insync.replicas` 설정이 함께 맞춰져야 진짜 의미가 생깁니다.
- \"안정성\"을 **장애 상황에서도 시스템이 계속 쓰기를 받아줄 수 있는가(가용성)**로 본다면:
  - **acks=1**이 더 유리합니다.
  - 팔로워가 느리거나 ISR이 줄어들어도 리더만 살아 있으면 계속 쓰기 가능하기 때문입니다.

결국, **안정성**이란 단어 안에는:

- **내구성(durability)**: 데이터를 안 잃는 것
- **가용성(availability)**: 장애 상황에서도 계속 서비스가 되는 것

두 가지가 함께 들어 있습니다.

> - **데이터를 최대한 안 잃고 싶은가?** → `acks=all` + `replication.factor >= 3` + `min.insync.replicas >= 2`  
> - **시스템이 항상 쓰기를 받아들이는 게 더 중요한가?** → `acks=1` + 적절한 재시도 + 멱등성

실제 서비스에서는 **주제(토픽)별로 acks 전략을 분리**하는 것이 가장 현실적인 접근입니다.

- 주문/결제/재고: **acks=all**
- 로그/메트릭: **acks=0 또는 1**
- 일반 도메인 이벤트: **acks=1 또는 all (도메인 중요도에 따라 결정)**

---

## 마무리

- **acks=1과 acks=all의 가장 큰 차이는 \"리더만 믿느냐, 리더 + 팔로워까지 모두 확인하느냐\"입니다.**
- **내구성만 놓고 보면 acks=all이 확실히 더 안전하지만, 가용성과 성능은 떨어질 수 있습니다.**
- **정답은 하나가 아니라, 토픽의 성격(돈/재고/로그 등)에 따라 acks 설정을 다르게 가져가는 것**입니다.
