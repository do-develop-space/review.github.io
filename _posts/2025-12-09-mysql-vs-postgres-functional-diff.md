# MySQL vs PostgreSQL: 2025년 12월 기준 기능적 차이 정리

실무에서 가장 많이 고민하게 되는 데이터베이스 선택 중 하나가 **MySQL vs PostgreSQL**입니다.  
두 제품 모두 성숙한 오픈소스 RDBMS이지만, **지향점과 강점이 꽤 다르기 때문에** 프로젝트 성격에 따라 선택이 갈리게 됩니다.

이 글에서는 2025년 12월 시점을 기준으로, MySQL과 PostgreSQL의 **기능적인 차이**를 중심으로 비교해보겠습니다. (버전 세부 스펙보다는 “어떤 성격의 프로젝트에 어떤 DB가 어울리는가?”에 초점을 둡니다.)

---

## 1. 기본 철학과 아키텍처 지향점

### PostgreSQL: “확장 가능한 객체-관계형 DB”

- 슬로건부터 **“The World’s Most Advanced Open Source Relational Database”** 를 내세움
- 전통적인 RDBMS에 더해, **객체-관계형(Object-Relational)** 개념을 강하게 지원
- “표준 준수(ANSI SQL) + 확장성 + 복잡한 데이터 모델”에 초점을 맞춘 느낌

### MySQL: “단순·빠른 웹 서비스용 RDBMS”

- 초기부터 LAMP 스택의 표준 DB로 자리 잡으면서 **웹 애플리케이션에 최적화된 RDBMS** 이미지를 가짐
- 다양한 스토리지 엔진 구조(InnoDB, MyISAM 등)를 제공하지만, 실질적으로는 **InnoDB 중심**
- “간단한 스키마 + 높은 읽기 성능 + 쉬운 운영” 쪽에 무게

요약하면:

- **PostgreSQL**: 기능 풍부, 확장성·표현력 강함
- **MySQL**: 단순·빠름, 웹·OLTP 위주의 워크로드에 친숙

---

## 2. 데이터 타입과 확장성

### PostgreSQL

- 다양한 **고급 데이터 타입** 지원
  - `JSONB`, `ARRAY`, `HSTORE`, `RANGE`, `UUID`, `XML` 등
  - 지리 정보 타입(PostGIS 확장) 등 강력한 확장 생태계
- **사용자 정의 타입, 연산자, 함수, 인덱스 메서드**를 만들 수 있는 높은 확장성
- JSON 처리에서도 `JSONB` 인덱싱, 함수들이 잘 정비되어 있어 **반-문서형 스토리지**처럼 활용 가능

### MySQL

- 전통적인 RDBMS 타입에 충실
  - `JSON` 타입은 있지만, PostgreSQL의 `JSONB`만큼 유연한 조회·인덱싱 기능은 상대적으로 제한적
- 사용자 정의 타입보다는 **기본 제공 타입 중심**으로 사용하는 경우가 많음

**정리**  
복잡한 스키마, 다양한 타입, JSON/지리 정보 등을 활용해야 한다면 **PostgreSQL이 유리**한 편이고,  
상대적으로 단순한 테이블 구조라면 **MySQL로도 충분**한 경우가 많습니다.

---

## 3. 트랜잭션, 동시성 제어, ACID

### PostgreSQL

- 강력한 **MVCC(Multi-Version Concurrency Control)** 구현
- 읽기/쓰기 동시성에서 **일관성 수준이 높고 예측 가능**한 편
- 트랜잭션 격리 수준, 락 처리, 복잡한 트랜잭션 시나리오에서 안정적인 동작으로 평가받음

### MySQL (InnoDB 기준)

- InnoDB 역시 MVCC를 사용하지만, 구현 디테일이 PostgreSQL과 다름
- 실무에서 주로 **읽기 많은 웹 서비스**에 최적화되어 있다는 평가
- ACID는 InnoDB 기준으로 잘 지원되지만, 과거 일부 스토리지 엔진(MyISAM 등)은 트랜잭션 미지원

**정리**  
트랜잭션·동시성 측면에서 두 DB 모두 성숙하지만, **복잡한 트랜잭션·락 시나리오**를 다룰 때는 PostgreSQL이 더 선호되는 경우가 많습니다.

---

## 4. 쿼리 기능, 표준 준수, 고급 기능

### PostgreSQL

- **ANSI SQL 표준 준수**에 더 가깝고, 윈도우 함수, CTE, 서브쿼리 등 고급 기능을 적극적으로 지원
- **뷰(View), 머티리얼라이즈드 뷰(Materialized View)**, 함수 기반 인덱스 등 풍부한 기능
- **CTE(공통 테이블 식)** 를 이용한 복잡한 리포팅/통계 쿼리에 강함

### MySQL

- 실용적인 기능 위주로 발전해 왔고, 과거에 비해 많은 부분이 개선되었지만,
- 일부 고급 SQL 기능 구현에서 **PostgreSQL보다 제약**이 있는 편
- 단순한 CRUD, 인덱싱, 조인 정도의 쿼리는 매우 빠르게 처리

**정리**  
복잡한 보고서·통계 쿼리, SQL 표현력이 중요한 시스템이면 **PostgreSQL 쪽이 더 편안**한 경우가 많습니다.

---

## 5. 성능 관점: 읽기/쓰기, OLTP/OLAP

### MySQL

- 전통적으로 **읽기 성능에 강점**이 있다는 인식
- 단순한 조합의 OLTP 트래픽, 고QPS 웹 서비스에서 널리 사용

### PostgreSQL

- 복잡한 쿼리·조인·함수 기반 처리에서 강점
- 단순 OLTP뿐 아니라, 어느 정도의 **분석성 쿼리(OLAP에 가까운 조회)** 까지도 다룰 수 있음

물론 2025년 시점에서는 **튜닝·인덱스 설계·하드웨어·클라우드 매니지드 서비스**에 따라 성능 프로파일이 크게 갈리기 때문에, “무조건 A가 빠르다” 식의 일반화는 무리입니다.  
다만 **워크로드 패턴**(단순 읽기 위주 vs 복잡한 분석·통계 위주)에 따라 선택의 방향이 어느 정도 갈립니다.

---

## 6. 복제, 샤딩, HA(고가용성)

두 DB 모두:

- 마스터-슬레이브(또는 프라이머리-레플리카) 복제 지원
- 클러스터링/HA 솔루션 생태계가 풍부

### PostgreSQL

- 논리 복제(Logical Replication), 물리 복제(Physical Replication) 모두 지원
- Patroni, repmgr, pgpool-II 등 **HA/Failover 솔루션**이 다양

### MySQL

- 레플리케이션 기능이 오래 전부터 널리 쓰여 왔고,
- Percona, Galera Cluster 등 다양한 HA/클러스터 옵션 존재

실무에서는 **클라우드 매니지드 서비스(RDS, Cloud SQL, Aurora 등)** 를 사용하는 경우가 많기 때문에,  
“DB 자체 기능 + 클라우드 매니지드 옵션”을 같이 보고 선택하는 것이 현실적입니다.

---

## 7. JSON, 반-문서형 워크로드

NoSQL이 유행한 이후, 두 DB 모두 JSON 지원을 강화해 왔습니다.

- **PostgreSQL**
  - `JSONB` 타입, GIN 인덱스, 다양한 JSON 함수 제공
  - “관계형 + 문서형을 섞어서 쓰기”에 매우 강함
- **MySQL**
  - `JSON` 타입 지원, 일부 인덱싱·함수 제공
  - 문서형까지 본격적으로 끌고 가기보다는 **부가적인 필드** 정도로 쓰는 경우가 많음

문서형 데이터 비중이 크다면,

- 완전한 NoSQL(예: MongoDB)를 고려하거나,
- RDBMS 안에서 처리하고 싶다면 **PostgreSQL의 JSONB**가 더 편리한 경우가 많습니다.

---

## 8. 라이선스, 생태계, 클라우드 지원

- **MySQL**
  - Oracle이 소유, 커뮤니티 에디션은 GPL
  - MariaDB, Percona Server 등 파생 프로젝트가 많음
- **PostgreSQL**
  - PostgreSQL License (BSD 계열)로, 상용 제품에 포함해도 제약이 적음

클라우드:

- 주요 클라우드(AWS, GCP, Azure) 모두 MySQL/PostgreSQL 매니지드 서비스를 제공
- Aurora(MySQL/PostgreSQL 호환), AlloyDB(PostgreSQL 호환) 등 **호환 엔진**들도 빠르게 발전 중

새로운 프로젝트라면, **사용하려는 클라우드에서 어떤 엔진을 더 잘 지원하는지**(성능, 모니터링, 백업/복구, 장애 대응 도구 등)도 함께 보는 것이 좋습니다.

---

## 9. 어떤 상황에 어떤 DB를 고려할까?

아주 러프하게 정리하면 다음과 같은 감각으로 볼 수 있습니다.

- **MySQL을 먼저 떠올릴 수 있는 경우**
  - 전형적인 웹 서비스, 비교적 단순한 도메인 모델
  - 읽기 많은 OLTP, 고QPS 웹 트래픽
  - 팀이 이미 MySQL 경험이 많고, 운영 노하우가 쌓여 있는 경우

- **PostgreSQL을 먼저 떠올릴 수 있는 경우**
  - 복잡한 도메인, 다양한 타입(JSONB, 지리 정보 등)을 적극적으로 쓰는 서비스
  - 리포팅/통계/분석성 쿼리가 많고, SQL 표현력이 중요한 경우
  - 향후 OLAP/검색/분석 시스템과의 연계(예: ClickHouse, Druid 등)에서 **표준 SQL·확장성**을 중시하는 경우

---

## 10. 정리 및 마무리

이 글에서는 2025년 12월 기준으로 MySQL과 PostgreSQL의 기능적 차이를,  
철학·데이터 타입·트랜잭션·쿼리 기능·성능 특성·JSON 지원 등 관점에서 정리해보았습니다.

- **MySQL**은 여전히 **단순한 스키마 + 빠른 OLTP + 웹 서비스** 환경에서 강력한 선택지이고,
- **PostgreSQL**은 **표현력 있는 SQL, 다양한 타입, 확장성**을 살리고 싶은 서비스에서 매력적인 옵션입니다.

저는 프로젝트의 도메인 복잡도, 트래픽 패턴, 팀의 경험과 운영 역량을 기준으로 MySQL과 PostgreSQL 중 무엇을 선택할지 비교해보면서, 각 데이터베이스의 장단점을 더 깊게 공부하고 있습니다.  
향후에는 PostgreSQL 위에 분석용 OLAP 시스템(ClickHouse, Druid 등)을 어떻게 얹을지, 그리고 MySQL·PostgreSQL을 혼합 사용하는 아키텍처 패턴도 정리해볼 예정입니다.

데이터베이스 선택과 함께 중요한 것은 **서비스 간 통신의 안정성**입니다. 마이크로서비스 아키텍처에서 한 서비스의 장애가 다른 서비스로 전파되는 것을 막기 위해 **Circuit Breaker 패턴**을 적용하는 방법을 다음 글에서 정리해보겠습니다. 🗄️
