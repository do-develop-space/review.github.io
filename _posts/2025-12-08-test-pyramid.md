# 테스트 피라미드(Test Pyramid): 단위·통합·E2E 테스트 어떻게 나눌까?

테스트 자동화를 하다 보면 이런 고민이 생깁니다.

- “단위 테스트만 열심히 쓰면 충분한가?”
- “통합 테스트는 얼마나 해야 하지?”
- “E2E 테스트는 느리고 불안정한데, 어디까지 가져가야 하지?”

이때 방향을 잡는 데 도움을 주는 개념이 바로 **테스트 피라미드(Test Pyramid)** 입니다.  
이번 글에서는 테스트 피라미드의 기본 개념과 각 층(단위/통합/E2E)을 어떻게 바라보고 설계할지 정리해보겠습니다.

---

## 1. 테스트 피라미드란?

테스트 피라미드는 흔히 다음과 같은 그림으로 표현됩니다.

```
        ┌───────────────┐
        │   E2E Tests   │   (적은 수, 고비용)
        └───────▲───────┘
                │
        ┌───────┴───────┐
        │ Integration   │   (중간 정도)
        │    Tests      │
        └───────▲───────┘
                │
        ┌───────┴───────┐
        │   Unit Tests  │   (많은 수, 저비용)
        └───────────────┘
```

핵심 아이디어:

- **아래로 갈수록(단위 테스트) 빠르고 싸며, 개수가 많아야 한다.**
- **위로 갈수록(E2E) 느리고 비싸며, 개수는 적어야 한다.**

즉, 모든 것을 E2E로만 때우려 하지 말고,  
**가능한 많은 검증을 단위/통합 테스트에서 소화**하고,  
E2E는 “진짜로 전체 플로우를 검증해야 하는 최소한의 시나리오”에 집중하자는 생각입니다.

---

## 2. 단위 테스트(Unit Test)

### 목적

- **아주 작은 단위(함수, 메서드, 클래스)의 로직**을 빠르게 검증
- 외부 의존성(DB, 네트워크, 파일 등)을 최대한 격리(Mock/Stubs)

### 특징

- 실행 속도가 매우 빠름 (수백~수천 개도 금방 실행)
- 실패 시 **원인 파악이 쉽다** (어디서 깨졌는지 바로 보임)

### 예시 (Java/Spring)

```java
@ExtendWith(MockitoExtension.class)
class OrderPriceCalculatorTest {

    @InjectMocks
    private OrderPriceCalculator calculator;

    @Test
    void 주문_총액을_정상적으로_계산한다() {
        List<OrderLine> lines = List.of(
            new OrderLine("상품A", 10000, 2),
            new OrderLine("상품B", 5000, 1)
        );

        int total = calculator.calculateTotalPrice(lines);

        assertThat(total).isEqualTo(25000);
    }
}
```

단위 테스트는 **도메인 로직, 계산 규칙, 분기 처리** 등을 집중적으로 검증하는 데 가장 효율적입니다.

---

## 3. 통합 테스트(Integration Test)

### 목적

- **여러 모듈/컴포넌트가 함께 동작할 때** 문제가 없는지 검증
- DB, 메시지 브로커, 외부 API 등 실제 의존성을 연결해 보는 경우가 많음

### 특징

- 단위 테스트보다 느리지만, E2E보다는 빠른 편
- 실패 시 “어디가 문제인지” 단위 테스트보다는 조금 더 어렵지만, 그래도 추적이 가능

### 예시 (Spring Boot 통합 테스트)

```java
@SpringBootTest
@AutoConfigureMockMvc
class OrderControllerIntegrationTest {

    @Autowired
    private MockMvc mockMvc;

    @Test
    void 주문을_생성하고_조회할_수_있다() throws Exception {
        // 주문 생성
        mockMvc.perform(post("/api/orders")
                .contentType(MediaType.APPLICATION_JSON)
                .content("""
                    {"userId": "user-1", "items": [{"productId": "p1", "quantity": 2}]}
                """))
            .andExpect(status().isCreated());

        // 주문 목록 조회
        mockMvc.perform(get("/api/orders?userId=user-1"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$[0].items[0].productId").value("p1"));
    }
}
```

통합 테스트에서는:

- 컨트롤러 ↔ 서비스 ↔ 리포지토리 간 연동,
- 실제 DB/트랜잭션 동작,
- 메시지 큐/이벤트 발행 등

**“경계가 만나는 부분”** 을 검증하는 데 중점을 둡니다.

---

## 4. E2E 테스트(End-to-End Test)

### 목적

- 사용자의 실제 시나리오를 **시스템 전체 관점에서** 검증
- 프론트엔드·백엔드·DB·외부 시스템까지 연결된 상태에서 테스트

### 특징

- 가장 느리고, 환경 셋업·유지 비용이 큼
- 실패 시 원인 분석이 가장 어렵고, **플레이키(Flaky) 테스트**가 되기 쉽다.

### 예시

- Cypress, Playwright 등을 이용한 브라우저 E2E 테스트
- 실제 API Gateway → BFF → 여러 마이크로서비스 → DB까지 연결된 상태에서의 시나리오 테스트

예:

- “신규 회원 가입 → 이메일 인증 → 첫 주문 → 마이페이지에서 주문 내역 확인” 전체 플로우

E2E 테스트는 **“정말로 중요한 비즈니스 플로우 몇 개만”** 두고,  
나머지는 단위/통합 테스트에서 커버하도록 설계하는 것이 현실적인 전략입니다.

---

## 5. 테스트 피라미드를 실제로 어떻게 적용할까?

### 1) 비율 감각 잡기

정답은 없지만, 자주 언급되는 감각적인 비율은 다음과 같습니다.

- 단위 테스트: 통합 테스트: E2E 테스트 ≈ **70 : 20 : 10**

즉,

- **대부분의 로직은 단위 테스트**로 커버하고,
- 경계·연동 부분은 통합 테스트,
- 핵심 사용자 플로우만 E2E로 가져가는 형태입니다.

### 2) 새로운 기능을 만들 때의 순서

1. 도메인 규칙, 계산 로직 → **단위 테스트** 먼저
2. API/DB 연동, 메시지 발행 등 → **통합 테스트**
3. 정말 중요한 시나리오라면 → **E2E에 추가할지 검토**

이 순서를 의식하면, 자연스럽게 테스트 피라미드 구조에 가까워집니다.

---

## 6. 정리 및 마무리

이 글에서는 테스트 피라미드 개념을 기준으로 단위·통합·E2E 테스트의 역할과 차이를 정리해보았습니다.

- 단위 테스트: 빠르고 싸고 많아야 하는, **로직 검증의 핵심**
- 통합 테스트: 컴포넌트와 인프라의 **연동 검증**
- E2E 테스트: 실제 사용자 플로우 중심의 **최종 안전망**

저는 테스트 피라미드 개념을 기반으로, 각 서비스에서 어떤 부분을 단위/통합/E2E로 가져갈지 패턴을 정리하면서, CI 파이프라인과 어떻게 연결할지 공부해 나가고 있습니다.  
앞으로는 서비스 규모와 팀 상황에 따라 테스트 피라미드를 어떻게 현실적으로 조정할 수 있을지, 그리고 성능 테스트(JMeter/nGrinder)와도 어떻게 조합할지 더 깊게 살펴볼 예정입니다. ✅
