# GitHub 기반 스펙 문서화와 협업 흐름 정리

서비스가 커질수록 “코드는 있는데, 왜 이렇게 서로 다르게 이해하고 있지?”라는 문제가 자주 생깁니다.  
이때 중요한 것이 **스펙(Spec) 문서화와 코드·GitHub와의 연결**입니다. 이번 글에서는 GitHub를 중심으로 **스펙 문서를 어떻게 관리하고 협업 흐름에 녹일지** 정리해보겠습니다.

---

## 1. 왜 GitHub에 스펙을 두는가?

전통적으로 스펙 문서는 Notion, Confluence, Google Docs 등에 흩어져 있는 경우가 많습니다.  
이렇게 되면:

- 문서는 최신인데 코드가 따라가지 못하거나,
- 코드는 먼저 바뀌었는데 문서가 그대로라서,
- “도대체 무엇이 진실인가?” 문제(SSOT, Single Source of Truth)가 생깁니다.

그래서 많은 팀이 **스펙 문서를 Git 리포지토리 안에서 관리**하는 방식을 도입합니다.

장점:

- 문서도 코드처럼 **버전 관리** 가능 (PR, 리뷰, revert)
- “이 변경(PR)이 어떤 스펙과 관련 있는지”를 쉽게 추적
- 브랜치 전략과 맞춰서 문서도 같이 관리

---

## 2. 어떤 종류의 스펙을 GitHub에 둘까?

### 1) 기능 스펙(Feature Spec)

- 화면/기능 단위 요구사항 정리
- 예: “주문 내역 조회 API”, “장바구니 저장 방식”

구조 예시:

```
docs/
  features/
    2025-12-06-order-history.md
    2025-12-06-cart-behavior.md
```

### 2) API 스펙 (REST/GraphQL 등)

- 엔드포인트, 요청/응답 스키마, 에러 코드 정의
- OpenAPI(Swagger) 스펙 파일과 함께 관리하면 좋습니다.

예시:

```
api-specs/
  openapi.yaml
  graphql/
    schema.graphqls
```

### 3) 아키텍처 결정 기록(ADR, Architecture Decision Record)

- “왜 이 기술/패턴을 선택했는지”를 남기는 문서
- 나중에 기술 선택을 되돌아볼 때 유용합니다.

예시:

```
adr/
  0001-use-bff-pattern.md
  0002-choose-kafka-over-rabbitmq.md
```

---

## 3. 스펙 문서와 PR을 어떻게 연결할까?

### 1) 스펙 먼저, 코드 나중 (Spec-first)

흐름:

1. `docs/` 아래에 스펙 초안 작성 (또는 수정)
2. 스펙만 담긴 PR 생성
3. 리뷰어와 함께 논의·수정
4. 스펙 확정 후 구현 PR 진행

장점:

- **요구사항을 먼저 정리**한 뒤 구현에 들어갈 수 있다.
- 코드 리뷰 단계에서 “스펙과 맞는가?”를 기준으로 판단 가능.

단점:

- 문서-구현 사이에 시간 차이가 길어지면 다시 어긋날 수 있음.

### 2) 스펙과 구현을 한 PR에 묶기

흐름:

1. 스펙 문서와 코드를 한 브랜치에서 함께 변경
2. 하나의 PR에서 “스펙 + 구현”을 동시에 리뷰

장점:

- “문서와 코드가 같이 바뀌는지”를 강제할 수 있음.

단점:

- PR이 커지기 쉬움 → 리뷰 부담 증가

실무에서는 **중요한 변경(새 아키텍처, 큰 기능)** 은 “스펙 PR → 구현 PR”로 나누고,  
작은 변경은 “스펙+구현 한 번에” 처리하는 식으로 섞어서 쓰게 됩니다.

---

## 4. 템플릿과 체크리스트 활용하기

### 1) 스펙 문서 템플릿

예를 들어 기능 스펙은 다음과 같이 통일할 수 있습니다.

```markdown
# 기능명

## 배경
- 왜 이 기능이 필요한가?

## 요구사항
- [ ] 사용자 스토리 1
- [ ] 사용자 스토리 2

## API/데이터 설계
- 엔드포인트, 요청/응답, 필드 정의

## 검증 방법
- 테스트 시나리오, 엣지 케이스
```

템플릿을 맞춰두면 나중에 보더라도 **문서의 구조가 일정해서 읽기 편해집니다.**

### 2) PR 템플릿

GitHub의 `.github/pull_request_template.md`를 활용해,  
PR 생성 시 다음 항목을 자동으로 체크하도록 할 수 있습니다.

```markdown
## 관련 스펙
- [ ] docs/features/... 링크
- [ ] ADR 링크 (있다면)

## 변경 요약
-

## 테스트
- [ ] 단위 테스트
- [ ] 통합 테스트
```

## 5. 정리 및 마무리

이 글에서는 GitHub 리포지토리 안에서 스펙 문서를 관리하는 이유와,  
기능 스펙·API 스펙·ADR 같은 문서들을 어떻게 구조화하고 PR 흐름과 연결할지 정리해보았습니다.

저는 GitHub 기반으로 스펙과 코드를 한 곳에서 관리하는 방식, 그리고 스펙-first / 구현-first 전략을 상황에 맞게 섞어 쓰는 방법을 공부하면서, 실제 팀 협업에 어떻게 적용할지 고민하고 있습니다.
