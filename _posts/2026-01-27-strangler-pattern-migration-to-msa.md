런타임 환경의 안정성을 높이는 방법을 정리했습니다.  
이번 글에서는 애플리케이션 아키텍처 차원에서 **기존 시스템을 어떻게 점진적으로 MSA로 옮겨갈 것인지**에 대한 패턴,  
즉 **Strangler(스트랭글러) 패턴**을 공부하는 느낌으로 정리해보겠습니다.

---

## 1. Strangler 패턴이란?

먼저 정의부터 짚고 가겠습니다.

> **Strangler(스트랭글러) 패턴**이란,  
> **시스템이 정상적으로 돌아가는 상태에서 점진적으로 MSA 아키텍처로 코드를 분리해 나가는 디자인 패턴**입니다.

이름은 “Strangler Fig(목을 조르는 무화과 나무)”에서 따왔습니다.

자연에서 Strangler Fig는:

1. 기존 나무 주변에 뿌리를 내리고
2. 조금씩 기어오르며 기존 나무를 감싸고
3. 시간이 지나면 기존 나무는 사라지고 새로운 나무만 남는

형태를 보입니다.

소프트웨어에서 이 비유를 적용하면:

- **기존 모놀리스 시스템을 한 번에 뜯어고치지 않고**,  
  옆에 새로운 MSA 컴포넌트를 붙여 나가며
- **점점 기존 부분을 대체하고 마지막에 모놀리스는 사라지게 만드는 전략**입니다.

---

## 2. 왜 Strangler 패턴이 필요한가?

### 2.1 “빅뱅 리라이트”의 위험성

모놀리스를 MSA로 옮기는 가장 단순한 생각은:

> "새로운 MSA 시스템을 한 번에 다 만들고,  
>  어느 날 전체 트래픽을 새 시스템으로 스위치하자."

하지만 현실에서는:

- 새 시스템 개발/테스트에 시간이 오래 걸리고
- 요구사항은 그 사이에도 계속 바뀌며
- 릴리스 시점에 **큰 장애가 날 가능성**이 매우 높습니다.

이를 흔히 **빅뱅 리라이트(Big-Bang Rewrite)** 라고 부르며,  
실패 사례가 아주 많습니다.

### 2.2 Strangler 패턴의 장점

Strangler 패턴은 이 리스크를 줄이기 위해:

1. **기존 시스템을 계속 운영하면서**
2. **일부 기능만 새로운 서비스로 조금씩 대체**하고
3. **트래픽을 점진적으로 전환**해 나가는 접근입니다.

장점은:

- 장애 시 **롤백 범위가 작음**
- 새 구조를 **실제 트래픽으로 조금씩 검증** 가능
- 비즈니스 팀/사용자는 **큰 “D-Day” 없이 자연스럽게 전환**

---

## 3. 전체 흐름: 모놀리스 → MSA로 천천히 옮기기

Strangler 패턴의 전형적인 단계는 다음과 같습니다.

```text
1단계: 프런트 도어(Front Door) 만들기
2단계: 특정 기능을 새로운 서비스로 분리
3단계: 트래픽 라우팅을 새 서비스로 전환
4단계: 모놀리스에서 해당 기능 제거
5단계: 이 과정을 반복하며 모놀리스 축소
```

각 단계를 조금 더 풀어보겠습니다.

### 3.1 1단계: 프런트 도어(Front Door) 만들기

먼저 **“모든 요청이 거쳐가는 입구”**를 만듭니다.

- API Gateway (Spring Cloud Gateway, NGINX, Kong, Traefik 등)
- 혹은 LB 레벨에서의 라우팅

목표:

- 모든 요청이 **Gateway → (모놀리스 or 새 서비스)** 구조를 따르도록 만들기
- 이렇게 하면 나중에 특정 URL/도메인만 새 서비스로 라우팅하는 것이 쉬워집니다.

### 3.2 2단계: 특정 기능을 새로운 서비스로 분리

다음으로, 모놀리스의 기능 중에서:

- **경계가 비교적 명확한 도메인** (예: 주문, 결제, 리뷰)
- 혹은 **변경이 자주 일어나는 부분**

부터 하나 골라서 **새로운 MSA 서비스**로 떼어냅니다.

예:

- `order-service`를 별도 Spring Boot 애플리케이션으로 분리
- 새로운 DB 스키마를 설계하거나, 기존 DB를 공유하는 방식으로 시작

### 3.3 3단계: 트래픽을 새 서비스로 라우팅

Gateway에서 라우팅 규칙을 추가합니다.

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: http://order-service:8080
          predicates:
            - Path=/orders/**
```

- `/orders/**` 요청은 이제 모놀리스가 아니라  
  새로운 `order-service`로 전송됩니다.

이때 중요한 점:

- 초기에 100%를 새 서비스로 보내기 부담스럽다면
  - Canary Release, Traffic Splitting 등을 이용해 **일부 트래픽만 새 서비스로 보내는 전략**도 가능

### 3.4 4단계: 모놀리스에서 해당 기능 제거

새 서비스가 충분히 안정적으로 돌아가고:

- 모니터링(예: Pinpoint, Prometheus)으로 성능/에러율이 안정적인지 확인했다면,
- 모놀리스에서 해당 도메인(예: 주문 관련 코드)을 정리합니다.

이때:

- DB 마이그레이션 전략(Outbox, CDC, Dual Write 회피 등)을 함께 설계해야 함
- 단순히 “코드만 삭제”가 아니라 **데이터/이벤트 흐름**까지 점검 필요

### 3.5 5단계: 이 과정을 반복

이제 다른 도메인(예: 결제, 재고, 리뷰)에 대해서도:

- “프런트 도어 + 새 서비스 + 라우팅 전환 + 모놀리스 정리” 과정을 반복합니다.

최종적으로:

- 모놀리스는 점점 빈 껍데기가 되고
- 모든 기능이 MSA 서비스로 이전되면
- 모놀리스를 **완전히 제거**할 수 있습니다.

## 4. Strangler 패턴 설계 시 고려사항

### 4.1 경계 컨텍스트(Bounded Context) 나누기

무엇부터 분리할지 결정하려면:

- 도메인 모델을 바라보는 **Bounded Context**를 먼저 잡는 것이 좋습니다.
- DDD 관점에서:
  - 주문, 결제, 배송, 리뷰 등 **업무 경계**를 기준으로 나누고
  - 각 경계를 하나의 마이크로서비스로 옮겨가는 그림을 그립니다.

### 4.2 데이터 마이그레이션 전략

Strangler 패턴은 주로 **트래픽 흐름** 관점에서 이야기되지만,  
실제로는 **데이터 마이그레이션**이 가장 큰 난관입니다.

대표적인 전략:

- Outbox 패턴 + 이벤트 브로커(Kafka 등)
- CDC(Change Data Capture) 도입
- 초기에는 DB 스키마 공유 후, 점진적 분리

이 부분은 이전에 다뤘던 **Outbox 패턴, 멱등성, Kafka 기반 이벤트 설계 글**들과 함께 보는 것이 좋습니다.

### 4.3 모니터링/옵저버빌리티

Strangler 패턴을 적용하면:

- 요청이 Gateway → (모놀리스 or 새 서비스) → DB 로 흐르기 때문에
- **분산 트레이싱(APM)** 이 필수에 가깝습니다.

예:

- Pinpoint, Zipkin, Jaeger 등을 통해:
  - “이 요청이 기존 모놀리스로 갔는지, 새 서비스로 갔는지”
  - “어디에서 에러/지연이 발생했는지”
  를 추적할 수 있어야 안전하게 전환할 수 있습니다.

---

## 5. 언제 Strangler 패턴이 잘 맞는가?

### 5.1 적합한 상황

- 기존 시스템이 **이미 프로덕션에서 안정적으로 돌아가는 상태**
- 전체 리라이트(Big-Bang)가 **리스크/비용 측면에서 부담이 큰 경우**
- 도메인이 여러 개로 나뉘어 있고, 부분적으로라도 분리할 수 있을 때

### 5.2 불리한 상황

- 기존 시스템이 너무 단순해서, 차라리 **새로 만드는 게 더 싸게 먹히는 경우**
- 데이터/도메인 경계가 지나치게 꼬여 있어서  
  부분 분리가 오히려 더 복잡할 때

이럴 때는:

- Strangler 패턴을 쓰더라도 **어디까지 분리할지**를 현실적으로 정하고
- 일부 도메인은 여전히 모놀리스에 남기는 하이브리드 구조도 고려할 수 있습니다.

---

## 마무리

이 글에서는 **Strangler(스트랭글러) 패턴**을 통해:

- 기존 모놀리스 시스템을 운영 중단 없이
- 점진적으로 MSA로 분리해 나가는 전체 흐름을 살펴봤습니다.

**핵심 포인트:**

1. Strangler 패턴은 **“기존 시스템을 유지하면서, 옆에 새 시스템을 조금씩 키워나가는 전략”**이다.
2. 프런트 도어(Gateway)를 세우고, 기능 단위로 새 서비스로 라우팅을 전환한다.
3. 각 단계마다 모니터링/데이터 마이그레이션 전략을 함께 설계해야 한다.

다음 글에서는 이 Strangler 패턴을 **실제 예시(예: 주문/결제 도메인)를 가지고 단계별로 어떻게 적용할지**를 더 구체적으로 풀어보겠습니다. 🚀
